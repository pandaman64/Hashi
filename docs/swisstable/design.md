# SwissTable の設計

SwissTable は **オープンアドレス法** のハッシュテーブルである。バケットチェーン（リンクリスト）を持たず、単一の連続配列に要素を置く。衝突解決は線形探査ではなく、**グループ単位の二次的（三角数）探査** と、**1 バイトの制御メタデータ** による SIMD 並列フィルタを組み合わせる。

この設計の目標は次の通りである。

- 要素あたりのオーバーヘッドを **約 1 バイト** に抑える（従来の 8 バイトポインタや Robin Hood の 2 バイト距離より小さい）
- ルックアップ時の **キー比較回数を大幅に減らす**（H2 指紋で 128 分の 1 に間引く）
- キャッシュライン内で **16（または 8）スロットを一度に走査**する
- 最大負荷率を **7/8 = 87.5%** まで上げても探査長を短く保つ

## 1. 全体像

テーブルは論理的に二つの配列を持つ。

```
制御バイト ctrl[0 .. n)     スロット slot[0 .. n)
  1 byte / bucket              sizeof(T) / bucket
```

制御バイトは対応するスロットの状態を表す。

| 状態 | 意味 |
| --- | --- |
| EMPTY | 未使用。探査はここで打ち切ってよい |
| DELETED | 削除済み（墓石）。探査は継続する |
| FULL(h2) | 使用中。下位 7 ビットにハッシュ指紋 H2 を格納 |

探査は「1 スロットずつ」ではなく **Group**（幅 `W` の連続制御バイト）単位で進む。`W` は SIMD レジスタ幅に合わせて 16（SSE2）または 8（NEON / ポータブル）が典型である。

```
          Group 0              Group 1              Group 2
    +------------------+------------------+------------------+
ctrl| ..............   | ..............   | ..............   |
    +------------------+------------------+------------------+
slot| T T T T ...      | T T T T ...      | T T T T ...      |
    +------------------+------------------+------------------+
```

制御バイトをスロットから分離する理由は二つある。

1. SIMD 比較はバイト配列に対して最も効率が良い
2. 制御バイトだけを走査すると、1 キャッシュラインに多数の論理スロットが載る

## 2. ハッシュの分割: H1 と H2

64 ビット（または `size_t`）のハッシュ値 `h` を次のように分割する。

```
h = [ H2 (上位 7 bit) | 中間ビット | H1 として使う下位ビット ]
```

- **H1** = `h` を `usize` に切り詰めた値。初期バケット番号は `H1 mod n`（`n` が 2 の冪ならビットマスク）
- **H2** = 上位 7 ビット。FULL 制御バイトに書き込む指紋

H2 に上位ビットを使うのは、H1 が下位の `log2(n)` ビットをインデックスに使うため、**H1 と H2 の相関を避ける**ためである。ハッシュ関数には avalanche（全ビットにエントロピーが散る性質）が要求される。

H2 は 7 ビットなので、誤ってキー比較に進む確率は理想的には 1/128。Abseil の解析では、高負荷でも探査途上の「間違った」オブジェクト数 `k` は 32 未満であり、偽陽性比較は `find` あたり 1/8 回未満に収まる。

```
制御バイト（FULL）:  0 h h h h h h h
                     ^ MSB=0 で「使用中」
                       残り 7 bit が H2
```

EMPTY / DELETED は MSB=1 の特殊値として符号化し、「使用中かどうか」を符号ビットだけで判定できるようにする。具体的なビットパターンは実装ごとに異なる（[比較](comparison.md) を参照）。

## 3. 三角探査 (triangular probing)

初期位置は `p(0) = H1 mod n`。以降はグループ幅 `W` の倍数だけジャンプする。

```
stride_0 = 0
p(0)     = H1 mod n

stride_{i+1} = stride_i + W
p(i+1)       = (p(i) + stride_{i+1}) mod n
```

これは三角数を用いた二次探査である。

```
p(i) = W * i(i+1)/2 + H1    (mod n)
```

`n / W` が 2 の冪であれば、写像 `i ↦ i(i+1)/2 (mod n/W)` は全単射であり、**すべてのグループをちょうど一度ずつ訪れる**。証明は [Quadratic probing](https://en.wikipedia.org/wiki/Quadratic_probing) および [Fabian Giesen, *Triangular numbers mod 2^n*](https://fgiesen.wordpress.com/2015/02/22/triangular-numbers-mod-2n/) に詳しい。

性質:

- 最初のジャンプは `W`（今見ている Group の直後から線形に続く）
- 次は `2W`、その次は `3W`、…
- グループどうしは重ならない
- 非線形なので、同一 H1 に集中する HashDoS 的な長い鎖に対して比較的強い
- 実際にはほぼ探査しない。最初の Group で `W` 個の非 EMPTY を外す必要があるため

テーブルには **常に少なくとも 1 つの EMPTY** が必要である。そうでなければ「未発見」の判定ができず、探査が無限ループする。

## 4. 制御バイトの複製 (cloned control bytes)

SIMD は常に `W` バイトをまとめて読む。探査開始位置は任意のバイト境界なので、配列末尾付近では読みがラップアラウンドする。分岐なしにこれを扱うため、制御配列の末尾に **先頭のコピー** を置く。

```
ctrl:  [ 0 1 2 ... n-1 | extra... ]
                         ^ 末尾の複製領域
```

実装によって extra の長さは `W` または `W-1 + sentinel` である。書き込み時は本物の制御バイトと複製先の両方を更新する。小さなテーブル（`n < W`）では複製の配置が微妙になり、本物と複製の間に EMPTY が挟まる。

複製があるため、Group ロード自体はラップを気にしなくてよい。ただし **スロット配列には複製がない** ので、候補インデックスは必ず `mod n` で本物のスロットに戻す。

## 5. ルックアップ (find)

```
find(x):
  h  = hash(x)
  h2 = H2(h)
  pos = H1(h) mod n
  loop:
    g = load Group at ctrl[pos]
    for each bit in g.match(h2):
      i = (pos + bit) mod n
      if slot[i] == x: return found(i)
    if g.contains(EMPTY): return not_found
    pos = next triangular probe
```

重要な不変条件:

- EMPTY を含む Group に到達したら、それ以降に目的のキーはない（挿入も同じ探査順で最初の空きに置くため）
- DELETED は「マッチしない FULL」と同じ。探査は止まらない
- キー比較は H2 が一致したスロットに対してのみ行う

## 6. 挿入 (insert)

挿入は二段構成が基本である。

1. まず `find` 相当で既存キーを探す。あれば上書き（map）または何もしない（set）
2. 未存在なら、同じ探査列上で最初の **EMPTY または DELETED** に置く

```
insert_new(x):  # 未存在が前提
  pos = H1(hash(x)) mod n
  loop:
    g = load Group at ctrl[pos]
    if g has EMPTY or DELETED:
      i = first such index (mod n)
      # 小テーブルでは複製領域の偽 EMPTY を補正する必要あり
      slot[i] = x
      ctrl[i] = H2
      return
    pos = next triangular probe
```

負荷率が上限（通常 7/8）に達していたら、先に容量を倍にして再ハッシュする。

`growth_left`（あと何個 EMPTY を潰せるか）は tombstone と独立に管理する。DELETED を FULL に再利用しても `len` は増えるが、EMPTY は減らないので `growth_left` は減らさない。EMPTY を潰したときだけ `growth_left` を減らす。

## 7. 削除 (erase) と墓石

削除で無条件に EMPTY を書くと、そのスロットを越えて探査していたキーの `find` が途中で止まってしまう。

SwissTable の判定は局所的である。削除位置の前後 `W` バイトを見て、

```
empty_before = Group(ctrl[index - W]).match_empty()
empty_after  = Group(ctrl[index]).match_empty()

if empty_before.leading_zeros + empty_after.trailing_zeros >= W:
    ctrl[index] = DELETED   # この位置を含む「非 EMPTY の連続」が Group 幅以上
else:
    ctrl[index] = EMPTY     # 前後に EMPTY があるので探査はもともとここで止まる
    growth_left += 1
```

負荷率 7/8 では「幅 `W` の非 EMPTY 連続」は稀なので、tombstone はあまり増えない。小テーブル（`n < W`）はテーブル全体が 1 Group に収まり、常に EMPTY で止まれるため tombstone を置かない。

tombstone が増えすぎると `growth_left` が 0 になり、実要素数が少なくても再ハッシュ（in-place または新規確保）が走る。in-place 再ハッシュは FULL→DELETED、DELETED/EMPTY→EMPTY と一括変換してから、DELETED を理想位置へ詰め直す。

## 8. 負荷率

| テーブル規模 | 最大負荷 |
| --- | --- |
| グループに収まる小テーブル | ほぼ 1。ただし終了判定用に EMPTY を 1 つ残す |
| それ以外 | 7/8 = 87.5% |

7/8 は、16 幅グループあたり平均 2 個の EMPTY を残す選択である。EMPTY が全くないと探査が停止できない。

容量の表現は実装で分かれる。

- Abseil: スロット数 `capacity = 2^m - 1`（それ自体がビットマスク）
- hashbrown: バケット数 `buckets = 2^m`、`bucket_mask = buckets - 1`

どちらも「グループ数が 2 の冪」という三角探査の前提を満たす。

## 9. 空テーブル

空のマップにヒープ確保したくない。両実装とも **静的な EMPTY 制御バイト列** を指すシングルトンで空状態を表す。

- 最初の Group を読むと全部 EMPTY なので、find / insert 準備は「無い」と即判定できる
- 実際の insert では負荷率チェックが resize を起こし、そこで初めて確保する
- キー配列用ポインタは空状態ではダングリングしてよい（制御バイトだけ読む）

## 10. 再ハッシュ時の制約

制御バイトに残るのは H2 だけである。H1 は再計算できないので、**resize のたびに全要素をハッシュし直す**。ハッシュ関数が重いと resize が支配的になる。ハッシュ計算にマップ外部の状態（インターン等）が必要だと、`clear` や `clone` 以外の操作にもその状態を渡す必要が出る。

## 11. アルゴリズム上の不変条件

Lean などで形式化する際の核になる条件を列挙する。

1. **容量とグループ**: グループ数 `n / W` は 2 の冪（またはテーブル全体が 1 グループに収まる）
2. **EMPTY の存在**: `growth_left` の管理により、常に少なくとも 1 つの EMPTY がある
3. **挿入位置**: キー `x` は、その探査列上で最初の EMPTY/DELETED に置かれる
4. **find の停止**: 探査列上で最初の EMPTY を含む Group まで見れば、有無が確定する
5. **tombstone の必要性**: ある位置を EMPTY にしてよいのは、その位置をまたぐどの Group 窓も EMPTY を含むときだけ
6. **複製の一致**: `ctrl[i] = ctrl[clone(i)]`（`i < n`）
7. **FULL の指紋**: FULL スロットの制御バイトは、格納値の H2 に一致する
8. **負荷率**: `len + tombstones` 相当が `CapacityToGrowth(n)` を超えない（正確な定義は実装の `growth_left` による）

## 12. 公開 API 層との関係

SwissTable 本体は「スロットの配列 + 制御バイト」という低レベルテーブルである。その上に載るのは実装依存である。

| 層 | 役割 |
| --- | --- |
| 生テーブル | find / insert / erase / rehash。ハッシュ値と等価関数を外から受け取ることもある |
| set | スロット = キー |
| map | スロット = `(K, V)`。キーだけハッシュ・比較する |
| ノード版（Abseil） | スロット = ヒープ上のノードへのポインタ。ポインタ安定性を買う |

共通の性能上の注意:

- 再ハッシュで要素が移動する（フラット格納の場合、ポインタ／参照／イテレータは無効化される）
- 異種キー検索（heterogeneous lookup）は、ハッシュと等価が「透明」なときにキー型への変換を省略できる
